External Clients (Top Tier)  
Description: Systems or users accessing the service, such as transaction processing applications or compliance user interfaces.  

API Gateway (Entry Point)  
Description: Manages incoming requests, performs routing, and enforces fundamental security measures.

ComplianceValidatorService (Core Application Layer)  
Description: Java-based microservice responsible for rule validation processes
API Layer: REST endpoints (POST /validate, POST /validate/async, POST /rules/update).

Interceptors:
- Authentication: Validates client credentials and tokens.
- Request Validation: Ensures flowType and requestData are valid.
- Logging: Asynchronous logging to ELK stack.
- Metrics: Sends performance and usage metrics to Prometheus.
- Error Handling: Maps errors to predefined rule_error_codes.
- Caching: Retrieves data from Redis cache as needed.

Business Logic:
- Flow Handler: Maps flowType to corresponding rules via flow_rule_mappings.
- Client Configuration: Filters applicable rules based on client_rule_mappings and client_settings.
- Rules Engine: Executes precompiled rules using the Drools engine.
- Asynchronous Processing: Manages non-critical flows through message queue integration.

Interaction:
Receives requests via API Gateway.

Retrieves rules and mappings from MongoDB.

Checks Redis cache for existing data.

Enqueues asynchronous tasks to the message queue.

Returns appropriate HTTP responses.

Data Storage (Database Layer)  
Description: Utilizes MongoDB to store rules, mappings, and error codes.  

Representation: Diagram featuring a MongoDB instance with the following collections:  
- rules: Contains rule content, version information, ruleGroup, and errorCodeId.  
- flow_rule_mappings: Associates flowType with ruleIds, including priority data.  
- client_rule_mappings: Links clientId to ruleIds, with enabled status and priority details.  
- client_settings: Records configuration details such as whether allRulesEnabled is active for each client.  
- rule_error_codes: Stores errorCode and corresponding errorMessage.  
- rules_staging: Used for testing and validating new rules before deployment.  

Technologies: MongoDB optimized with indexes to ensure high performance.  

Interactions:  
- Queried by the ComplianceValidatorService to retrieve rules and configurations.  
- Updated through the rule management API as needed.

External Systems (Supporting Infrastructure)  
Description: Infrastructure components for caching, asynchronous processing, and system monitoring.

Representation: Separate modules for:  
- Redis: Responsible for caching rules, mappings, and error codes with a Time-to-Live (TTL) of 5 minutes.  
- Message Queue: Kafka or RabbitMQ used for asynchronous message processing and flow management.  
- Monitoring: Prometheus for metrics collection and ELK stack for log aggregation and analysis.

Technologies: Redis, Kafka/RabbitMQ, Prometheus, ELK stack.

Interactions:  
- Redis: Accessed via caching interceptors for read/write operations.  
- Message Queue: Handles asynchronous tasks and stores processing results in MongoDB.  
- Monitoring: Collects metrics and logs from interceptors for system oversight.
